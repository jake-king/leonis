# P5 — SDL3 + wgpu on mobile, from Rust, no hand-written native code

Verdict: **partial — Android pass on the emulator (dev box and CI), 2026-11-20.** iOS (simulator and
device) and a physical Android device are not yet run.

Probe: `probes/p5-android` — the P1 check (clear, present, read one pixel back, planted wrong colour
must fail) built as `libmain.so` exporting `SDL_main`. SDL's own Java activity
(`org.libsdl.app.SDLActivity`, compiled from the sdl3-src crate's copy of SDL 3.4.20) loads
`libSDL3.so` and `libmain.so` and calls `SDL_main`. No Java or Kotlin of ours; no Gradle.

`build-apk.sh <abi>` builds the APK with the SDK's tools only: cargo with the NDK r29 linker
(sdl3-sys builds SDL3 through the NDK's CMake toolchain), `javac --release 17` on SDL's Java, `d8`,
`aapt2 link` on a generated manifest, `zip`, `zipalign`, `apksigner` (a throwaway debug key, password
via the environment). `run-on-device.sh <apk> [shot.png]` installs, runs the probe and the control,
reads both verdicts from logcat (tag `leonis`), and — if asked for a screenshot — takes it after the
probe logs `p5 first_frame` and fails the run unless its centre pixel is the probe's colour.

The probe takes its mode from the `debug.leonis.p5` system property (`adb shell setprop`), because
reading intent extras needs Java.

## Runs

Dev box, emulator API 36 (Android 16), x86_64, `-gpu swiftshader_indirect`, KVM:
```
p5 setup driver=android backend=Vulkan adapter="SwiftShader Device (Subzero)" device_type=Cpu driver_name="SwiftShader driver" format=Rgba8UnormSrgb present_mode=Mailbox size=2400x1080
p5 result=pass plant=false frames=300 presented=300 skipped=0 occluded=0 reconfigures=1 pixel=[0, 188, 255, 255] expected=[0, 188, 255, 255] ms=4627
p5 result=fail plant=true frames=300 presented=300 skipped=0 occluded=0 reconfigures=1 pixel=[255, 0, 0, 255] expected=[0, 188, 255, 255] ms=1979
probe exit=0 control exit=1
screen 2400x1080 centre=(0, 188, 255) expected=(0, 188, 255) match
```
Screenshot: `p5/p5-android-emulator.png`. The arm64-v8a APK (for devices) also builds (6.1 MB).

CI (ubuntu-24.04, same SDK versions, KVM enabled), run 44775174888: booted in ~50 s, probe pass,
control fail (exit 1), 9,193 ms for 300 frames.

## Findings

- **SDL3 + wgpu reach an Android screen from Rust plus a shell script.** The only Java is SDL's.
- **The generated manifest must set a theme without a title bar.** With no theme, Android drew an
  action bar ("leonis P5") over the app while the surface still reported the full 2400x1080.
  `Theme.DeviceDefault.NoActionBar.Fullscreen` removed it.
- **Edge-to-edge is enforced:** the status bar and gesture bar are drawn over the app on Android 16
  even with a fullscreen theme. Safe areas (SPEC R31) are needed from the first app, not later.
- **SDL defaulted to landscape** (2400x1080). Orientation must be the app's explicit choice.
- `libSDL3.so` was built for API 21, not 29: the NDK CMake toolchain did not take `ANDROID_PLATFORM`
  from the environment. Harmless here; the real build passes it as a CMake define.

## The intermittent failure: an activity relaunch right after boot (root cause found)

After CI first went green, repeated runs failed about half the time: the frame loop ended early (41,
16, 2 of 300 frames), or wgpu said "surface not supported by adapter", or no verdict came at all.
It reproduced locally on every first launch after a cold boot through `run-on-device.sh` (4 of 4).
The log of a failing launch (timestamps from the dev box):

```
09:31:51.169 ActivityTaskManager: START ... cmp=org.leonis.p5/org.libsdl.app.SDLActivity
09:31:52.158 ActivityTaskManager: Config changes=80000000 ...          (CONFIG_ASSETS_PATHS)
09:31:52.603 BLASTSyncEngine: ActivityRecord{... org.leonis.p5/org.libsdl.app.SDLActivity} is relaunching
09:31:53.596 SDL: onPause()   ... surfaceDestroyed() ... onStop() ... onDestroy()
09:31:55.131 SDL: onCreate() ... activity finished
09:32:... OverlayManagerService finishes applying overlays on user unlock
```

Android keeps applying resource overlays after `sys.boot_completed`. Each one is a
`CONFIG_ASSETS_PATHS` configuration change, which an app cannot declare in `configChanges`, so the
activity is destroyed and recreated. **SDL3 does not survive that**: the second activity instance
finishes immediately and the thread running `SDL_main` dies with the first, so the probe never
reaches a verdict. Where the relaunch lands in the probe's run decides the symptom.

The same change happens on real phones when the user switches theme or wallpaper colours (Material
You), so **leonis must persist and restore app state across an activity relaunch** — a concrete P7
case.

Fix for the probe (`run-on-device.sh`): before installing, wait until no configuration change has
been logged for 10 s (up to 120 s), and at a timeout say whether the probe's activity was
relaunched. After the fix: 3 of 3 cold boots pass locally (each launched straight after boot).

Then two more causes, found by running more cold boots (CI run 44785387999 and five local boots):
- **The probe asked for wgpu's default (desktop) limits.** One CI adapter reported no compute
  (`max_compute_workgroups_per_dimension` 0) and device creation failed. The probe now logs the
  adapter and requests `adapter.limits()` — what the adapter offers. That is a leonis rule too.
- **"System UI isn't responding".** A freshly booted emulator on a software GPU starves System UI;
  the dialog covered the probe (which kept presenting underneath: 781 frames, correct pixel, nothing
  visible) and **does not go away on its own** (still up after 180 s). The probe also now runs at
  least 6 s, because 300 frames took ~1.5 s and ended before a screenshot could land.

`run-on-device.sh` now settles until there has been no configuration change for 10 s AND the launcher
has held focus for 10 s, and reports a screenshot covered by a "not responding" dialog as exit 2
(could not run) with the reason, never as a pass or a probe failure.

Five local cold boots after that, each launched straight away: **4 pass, 1 exit 2** (the dialog
appeared and stayed for 180 s), **0 false results**. Open: dismissing that dialog (untested; the
next step if CI hits it).

### Why "System UI isn't responding" happens (measured, 2026-11-20)

`boot-load.sh` sampled every 2 s for 180 s after each of 5 cold boots (AOSP API 36 image,
SwiftShader, 4 cores): CPU busy, load, top 3 processes, boot flag, focused window; and on the dialog,
`dumpsys cpuinfo` plus the ANR trace.

| Boot | boot_completed | Dialog | CPU busy, 20 s windows from adb connect |
|---|---|---|---|
| 1 | 35 s | no | 59% 74% 19% 3% 2% … |
| 2 | 29 s | no | 65% 67% 12% 3% 2% … |
| 3 | 28 s | no | 64% 69% 9% 2% 2% … |
| 4 | 31 s | **40 s** | 71% 72% 31% 2% 2% … |
| 5 | 33 s | **33 s** | 77% 74% 10% 3% 2% … |

- Every boot is a ~40 s burst (60–77% of 4 cores; `dumpsys cpuinfo`: 54–65% of it kernel time), then
  ~2%. Boots with and without the dialog have similar load, so load alone does not predict it.
- The dialog appears at boot completion, inside the burst. Both ANR traces (11:15:58, 11:19:23) say
  **"com.android.systemui failed to complete startup"**: System UI's main thread blocked in
  `SystemUIApplication.onCreate` on a binder call — to SurfaceFlinger (`getGpuContextPriority`) in
  boot 5, to the service manager in boot 4. Just before, SurfaceFlinger was at a full core:
  composition through SwiftShader is CPU work on this emulator.
- The system recovers within ~20 s, but **the dialog stays until dismissed** (180 s in an earlier run).
- Trap: `/data/anr` survives cold boots (the data partition is not wiped); match traces to a boot by
  timestamp. All four traces on this AVD (09:53, 09:57, 11:15, 11:19) give the same reason.

So the cause is a startup race between System UI and a CPU-bound SurfaceFlinger during the boot
burst — 2 of 5 cold boots here — not a fault in the app under test.

### Fix chosen by the operator: start every run from an idle snapshot

`emulator.sh prepare AVD` cold-boots, waits until the system is idle and clean (launcher focused, no
"not responding" dialog, no configuration change, CPU < 15% busy — all held 10 s), and saves snapshot
`leonis-ready`; a boot that shows the dialog is discarded and cold-booted again (up to 3), never
dismissed. `emulator.sh start AVD` boots from the snapshot without saving back. Locally: prepare took
one cold boot (idle 24 s after boot, CPU 2%), 93 s in total; then **5 of 5 starts + probe runs pass**,
every screenshot right on the first try. Each start came up with the same launcher window id
(`f65cdea`): the saved state, not a fresh boot.

Measured, against my own expectation: a snapshot start took **30–56 s** — no faster than a cold boot
(loading 1.9 GB of saved RAM). The snapshot buys a clean, idle start, not speed. In CI it only pays
off cached between runs: `actions/cache` keeps the AVD (3.1 GB with the snapshot), keyed on image,
emulator version and emulator settings; a cache miss prepares; a start that fails prepares again.

Wrong turns, kept for the record:
- **Google Play services' setup screen** (`CoverSheetWelcomeActivity`) did take the foreground in one
  CI run, so CI was switched to the plain AOSP image (`system-images;android-36;default;x86_64`). The
  AOSP image then reproduced the failure locally — Play services was not the cause. The AOSP image
  stays: fewer moving parts, and it allows `adb root` (needed for `debuggerd` stacks).
- A **missing panic message**: the probe logged `result=panic` with no reason, because Rust panics go
  to stderr, which Android discards. The probe now installs a panic hook that logs to logcat.

## CI fixes before that (each found by a diagnostic, not a guess)

1. `build-apk.sh` found no `libSDL3.so`: CI's cargo lays build scripts out as
   `build/sdl3-sys/<hash>/`, the dev box as `build/sdl3-sys-<hash>/`. Fix: take the copy sdl3-sys
   places in `target/<target>/release/`; pin Rust 1.99.1.
2. `adb wait-for-device` timed out before the emulator log was printed. Fix: poll, fail fast, print
   the log.
3. `Unknown AVD name`: avdmanager and the emulator disagreed on the AVD directory. Fix:
   `ANDROID_AVD_HOME`.
4. A screenshot taken at a fixed delay showed the launch animation. Fix: screenshot after the probe's
   first frame, retried until it shows the probe's colour (up to 10 tries), checked by
   `screen_pixel.py` (which rejects the bad CI screenshot).
